# HDU 校园网跨平台客户端设计

## 背景

当前仓库已经具备可用的 Go 命令行校园网登录能力，但仍停留在单一 CLI 形态。目标是把它升级为一套可交付产品：

- macOS 和 Windows 提供桌面客户端
- Linux 保持 CLI，但安装和常驻使用必须足够简单
- 三端共享同一套 Go 登录核心
- 使用 GitHub Actions 自动测试、打包并发布 GitHub Release
- 升级 Go 到最新稳定版本，并以此版本作为本地与 CI 的统一构建基线

## 目标

构建一套以共享 Go 核心为基础的校园网客户端产品，满足以下能力：

- 登录学校校园网
- 断线自动重连
- 开机自动连接
- 桌面端关闭窗口时最小化到托盘
- Linux 一键安装并自动部署后台常驻服务
- GitHub Actions 自动构建 macOS `.dmg`、Windows `.msi`、Linux CLI 二进制并发布 Release

## 非目标

本次设计不包含以下内容：

- Linux 图形桌面客户端
- 多学校、多认证协议支持
- 云同步、远程控制或网页管理后台
- 复杂账户体系或多人共享配置
- 过度美化的桌面 UI

## 方案选择

采用 `方案 A：单仓库多入口`。

### 选择原因

- 最大化复用现有 Go 校园网登录逻辑
- 共享测试、版本、发布链路，后期维护成本最低
- 最适合同时交付 Wails 桌面端和 Linux CLI
- 能在不拆仓的前提下逐步重构现有 CLI

### 放弃的方案

- `方案 B：桌面端单独新仓库`
  - 会导致登录逻辑拆分或重复
  - 版本同步和发布管理复杂
- `方案 C：桌面端仅作为 CLI 壳`
  - 托盘、自启动、状态同步和错误提示体验差
  - 不利于后续扩展

## 产品结构

整体采用“共享核心 + 多入口”架构：

- 共享 Go 核心负责校园网协议、状态检测、重连、配置、日志
- Linux CLI 作为命令行入口
- Wails 桌面端作为 macOS / Windows 图形入口
- GitHub Actions 统一完成测试、打包和发布

### 分层设计

- `internal/core`
  - 负责认证登录、登出、在线检测、重连状态机、配置装载、日志记录
- `internal/platform`
  - 负责自启动、系统凭据、托盘、平台差异处理
- `cmd/...`
  - 保留并重构为 Linux CLI 入口，只做参数解析和结果输出
- `desktop/wails`
  - Wails 前后端代码，负责设置窗口、托盘菜单、状态展示
- `.github/workflows`
  - CI、打包、Release 发布
- `scripts/`
  - Linux 一键安装脚本和辅助脚本

## 桌面端设计

桌面端采用 `托盘常驻 + 设置窗口` 形态，并默认支持 `开机自动连接`。

### 用户体验

- 首次启动时展示设置窗口
- 用户填写校园网地址、账号、密码、检测间隔等配置
- 保存后立即尝试连接
- 主窗口关闭时不退出，而是最小化到系统托盘
- 托盘图标常驻，显示当前连接状态
- 系统启动后自动拉起应用并自动连接

### 托盘菜单

托盘菜单至少包含：

- 连接
- 断开
- 打开设置
- 查看当前状态
- 开机启动开关
- 退出

### 状态展示

桌面端需要明确区分以下状态：

- 未配置
- 已断开
- 连接中
- 已连接
- 重连中
- 认证失败
- 网络不可达

### 自启动

- macOS：注册用户级开机启动
- Windows：注册用户级开机自启动
- 启动后如果配置完整，则自动尝试连接校园网

### 凭据存储

- macOS：使用系统 Keychain
- Windows：使用 Credential Manager
- 窗口内只展示账号，密码不明文回显

## Linux CLI 设计

Linux 保持 CLI 形态，但体验目标是“傻瓜式可用”，即安装和常驻尽可能自动化。

### 交付形态

- 提供 Linux CLI 二进制压缩包
- 提供一键安装脚本
- 提供用户级 `systemd --user` 服务

### 目标使用路径

理想路径应接近：

1. 用户执行一条安装命令
2. 脚本下载对应架构二进制
3. 脚本写入本地命令路径
4. 脚本引导输入校园网账号和密码
5. 脚本生成配置并自动注册、启动服务
6. 后续由后台自动保持在线

### 服务方式

Linux 使用 `systemd --user` 实现后台常驻：

- 不要求 root 安装
- 安装到当前用户目录
- 使用用户级服务完成开机启动和断线重连

### CLI 能力

CLI 至少保留和补充以下命令：

- `login`
- `logout`
- `status`
- `daemon run`
- `service install`
- `service enable`
- `service disable`
- `config init`

命令命名允许在实现计划阶段根据 Cobra 风格微调，但功能必须覆盖上面的职责。

### Linux 凭据存储

- 配置写入用户目录
- 密码默认存储在配置文件中
- 安装和保存时主动收紧文件权限，仅当前用户可读写

## 共享核心设计

现有 `pkg/srun` 中的协议实现继续复用，但需要把“命令式流程”抽为可复用服务层。

### 核心职责

- 校园网 challenge 获取
- 登录请求发送
- 登出请求发送
- 当前在线状态检查
- 外网可达性检查
- 自动重连调度
- 错误分类
- 配置与凭据读取
- 状态回调与日志输出

### 服务边界

共享核心对上层暴露稳定服务接口，而不是让 CLI 和桌面端直接拼装登录细节。

推荐拆分为以下责任单元：

- `AuthService`
  - 封装 challenge、login、logout
- `StatusService`
  - 封装用户在线状态和外网连通性检测
- `ReconnectManager`
  - 负责常驻检查和自动重连策略
- `ConfigStore`
  - 负责配置和凭据适配
- `AppState`
  - 维护当前连接状态并向桌面端 / CLI 输出事件

### 重连策略

重连流程需要具备以下行为：

- 定时检测当前是否仍然在线
- 如果状态失效，重新获取 challenge 并登录
- 如果外网不可达但校园网状态异常，先执行必要清理再重试
- 连续失败时进入指数退避，避免高频请求
- 恢复成功后重置退避计数

### 错误分类

至少区分以下错误类型：

- 配置缺失
- 凭据缺失
- 校园网地址不可达
- 认证失败
- 临时网络故障
- 后台服务注册失败
- 平台能力不可用

错误消息对 Linux CLI 采用清晰中文输出，对桌面端采用状态文案加必要弹窗。

## 配置设计

配置分为“公共配置”和“平台相关敏感信息”。

### 公共配置

公共配置至少包含：

- 校园网 endpoint
- ac_id
- 用户名
- 检测间隔
- 是否开机自动连接
- 是否启用自动重连
- 日志级别

### 敏感信息

- 桌面端密码放入系统凭据存储
- Linux 默认放入配置文件

### 兼容性

需要兼容现有 `.hdu-cli.yaml` 使用习惯，避免老 CLI 用户完全无法迁移。若结构发生变化，需要提供平滑迁移逻辑或兼容读取逻辑。

## 打包与发布设计

### Go 版本

- 将项目 Go 版本升级到最新稳定版本
- 本地 `go.mod`、CI 和打包流水线使用同一版本

### 产物

GitHub Release 需要至少包含：

- macOS `.dmg`
- Windows `.msi`
- Linux CLI 压缩包
- Linux 一键安装脚本
- 校验文件

### GitHub Actions

流水线分为三个大类：

- 共享核心测试
- Linux CLI 构建与发布
- Wails 桌面端构建与发布

建议职责如下：

- `test`
  - 安装最新稳定 Go
  - 运行 `go test ./...`
- `build-linux`
  - 构建 Linux CLI
  - 产出压缩包和安装脚本
- `build-desktop-macos`
  - 构建 Wails macOS 应用并打包 `.dmg`
- `build-desktop-windows`
  - 构建 Wails Windows 应用并打包 `.msi`
- `release`
  - 汇总产物
  - 创建 GitHub Release
  - 上传全部附件

## 测试设计

### 单元测试

为共享核心增加单元测试，覆盖：

- 配置加载
- 认证流程编排
- 在线状态判断
- 自动重连状态机
- 退避策略

### 集成测试

- 通过可替换接口 mock 校园网请求
- 校验 CLI 关键命令输出和退出码

### 打包验证

- CI 必须验证 Linux CLI 可构建
- 桌面端至少验证后端逻辑和打包流程可运行

UI 自动化不是本次硬性范围，但桌面端必须保留可测试边界。

## 迁移策略

为了降低风险，建议按以下顺序推进：

1. 抽取共享核心并补测试
2. 重构现有 CLI 接入共享核心
3. 增加 Linux 后台服务与一键安装脚本
4. 引入 Wails 桌面端
5. 完成 GitHub Actions 打包与 Release 发布

这样可以保证在桌面端完成前，Linux CLI 已经保持可用。

## 风险与约束

### 桌面端风险

- Wails 托盘、自启动、安装器细节存在平台差异
- `.dmg` 和 `.msi` 打包链路需要额外验证

### 现有代码风险

- 当前 CLI 逻辑较多直接耦合 Cobra / Viper，需要适度解耦
- 当前自动重连逻辑分散在命令实现中，需要抽出稳定服务层

### Linux 风险

- 某些发行版用户级 `systemd` 行为有差异
- 极简环境下需要对缺失 `systemctl --user` 提供降级提示

## 成功标准

满足以下条件即视为设计目标达成：

- macOS 和 Windows 用户可通过图形客户端完成校园网登录
- 应用可托盘常驻、关闭窗口最小化、开机自动连接
- 断线后可以自动重连
- Linux 用户可通过一条安装命令完成安装、配置和后台服务启用
- GitHub Actions 自动构建三端产物并发布 Release
- 项目切换到最新稳定 Go 版本并通过测试
